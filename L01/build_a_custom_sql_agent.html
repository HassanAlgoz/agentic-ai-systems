Build a custom SQL agent

In this tutorial, we will build a custom agent that can answer questions about a SQL database using LangGraph’s Functional API. A custom agent allows for deep control over the agent’s behavior, such as enforcing specific tool use and implementing human-in-the-loop review.

Setup

pip install langchain langgraph langchain-community

First, install the required packages to run the agent.

export LANGSMITH_TRACING="true"
export LANGSMITH_API_KEY="..."

Set up LangSmith tracing to inspect what is happening inside your agent workflow.

Configure the database

import requests, pathlib

url = "https://storage.googleapis.com/benchmarks-artifacts/chinook/Chinook.db"
local_path = pathlib.Path("Chinook.db")

if not local_path.exists():
    response = requests.get(url)
    if response.status_code == 200:
        local_path.write_bytes(response.content)
        print(f"File downloaded and saved as {local_path}")

We download the chinook SQLite database from a public bucket to have a ready-to-use digital media store dataset for our agent.

from langchain_community.utilities import SQLDatabase

db = SQLDatabase.from_uri("sqlite:///Chinook.db")

print(f"Dialect: {db.dialect}")
print(f"Available tables: {db.get_usable_table_names()}")

The SQLDatabase wrapper from langchain_community provides a simple interface to connect to the database, execute SQL queries, and fetch results.

Initialize Tools

from langchain_community.agent_toolkits import SQLDatabaseToolkit

# We assume `model` is a pre-configured LLM supporting tool-calling
toolkit = SQLDatabaseToolkit(db=db, llm=model)

tools = toolkit.get_tools()

get_schema_tool = next(tool for tool in tools if tool.name == "sql_db_schema")
run_query_tool = next(tool for tool in tools if tool.name == "sql_db_query")

We extract specific tools for getting schemas and running queries so we can explicitly assign them to dedicated agent tasks later on.

Warning

Building Q&A systems over SQL databases requires executing model-generated SQL queries. Make sure that your database connection permissions are scoped as narrowly as possible for your agent’s needs to mitigate risks of unauthorized or destructive operations.

Implementing Agent Tasks

from typing import TypedDict, List
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage, AnyMessage, ToolMessage
from langgraph.func import task, entrypoint

class AgentState(TypedDict):
    """Custom state for SQL agent."""
    messages: List[AnyMessage]

A custom AgentState schema provides a clean and predictable structure for managing the workflow’s messages between functional tasks.

Task 1: List Tables

@task
def list_tables(state: AgentState) -> AgentState:
    tool_call = {
        "name": "sql_db_list_tables",
        "args": {},
        "id": "abc123",
        "type": "tool_call",
    }
    tool_call_message = AIMessage(content="", tool_calls=[tool_call])

    list_tables_tool = next(tool for tool in tools if tool.name == "sql_db_list_tables")
    tool_message = list_tables_tool.invoke(tool_call)
    response = AIMessage(content=f"Available tables: {tool_message.content}")

    state["messages"].extend([tool_call_message, tool_message, response])
    return state

By forcing a predetermined tool call to list tables, we ensure the agent starts with complete awareness of the available tables without relying on the LLM to decide what to do first.

Task 2: Get Schema

@task
def call_get_schema(state: AgentState) -> AgentState:
    llm_with_tools = model.bind_tools([get_schema_tool], tool_choice="any")
    response = llm_with_tools.invoke(state["messages"])
    state["messages"].append(response)

    # Automatically execute the requested schema tool
    for tool_call in response.tool_calls:
        tool_message = get_schema_tool.invoke(tool_call)
        state["messages"].append(tool_message)
        
    return state

We force the model to use the schema tool (tool_choice="any") to fetch table schemas early in the process, guaranteeing that table schema context is available for accurately generating SQL queries.

Task 3: Generate Query

generate_query_system_prompt = """
You are an agent designed to interact with a SQL database.
Given an input question, create a syntactically correct {dialect} query to run,
then look at the results of the query and return the answer. Unless the user
specifies a specific number of examples they wish to obtain, always limit your
query to at most {top_k} results.

You can order the results by a relevant column to return the most interesting
examples in the database. Never query for all the columns from a specific table,
only ask for the relevant columns given the question.

DO NOT make any DML statements (INSERT, UPDATE, DELETE, DROP etc.) to the database.
""".format(
    dialect=db.dialect,
    top_k=5,
)

@task
def generate_query(state: AgentState) -> AgentState:
    system_message = SystemMessage(content=generate_query_system_prompt)
    
    llm_with_tools = model.bind_tools([run_query_tool])
    response = llm_with_tools.invoke([system_message] + state["messages"])

    state["messages"].append(response)
    return state

Here, we provide the generation prompt and allow the model to freely decide whether to output a query or provide a final answer, since we provide the run_query_tool without forcing it to invoke.

Task 4: Check Query

check_query_system_prompt = """
You are a SQL expert with a strong attention to detail.
Double check the {dialect} query for common mistakes, including:
- Using NOT IN with NULL values
- Using UNION when UNION ALL should have been used
- Using BETWEEN for exclusive ranges
- Data type mismatch in predicates
- Properly quoting identifiers
- Using the correct number of arguments for functions
- Casting to the correct data type
- Using the proper columns for joins

If there are any of the above mistakes, rewrite the query. If there are no mistakes,
just reproduce the original query.

You will call the appropriate tool to execute the query after running this check.
""".format(dialect=db.dialect)

@task
def check_query(state: AgentState) -> AgentState:
    system_message = SystemMessage(content=check_query_system_prompt)

    tool_call = state["messages"][-1].tool_calls[0]
    user_message = HumanMessage(content=tool_call["args"]["query"])
    
    llm_with_tools = model.bind_tools([run_query_tool], tool_choice="any")
    response = llm_with_tools.invoke([system_message, user_message])
    response.id = state["messages"][-1].id
    
    state["messages"][-1] = response
    return state

Inserting a validation task catches common SQL mistakes and automatically rewrites the query if necessary before it ever touches the database, vastly increasing query reliability.

Task 5: Run Query with Human-in-the-Loop Review

from langgraph.types import interrupt

@task
def run_query(state: AgentState) -> AgentState:
    last_message = state["messages"][-1]
    tool_call = last_message.tool_calls[0]
    
    request = {
        "action": run_query_tool.name,
        "args": tool_call["args"],
        "description": "Please review the tool call"
    }
    
    # Pause the graph and wait for user resumption
    response = interrupt(request)
    
    # Handle the human review response
    if response["type"] == "accept":
        tool_response = run_query_tool.invoke(tool_call)
    elif response["type"] == "edit":
        tool_input = response["args"]["args"]
        modified_tool_call = {
            "name": tool_call["name"],
            "args": tool_input, 
            "id": tool_call["id"], 
            "type": "tool_call"
        }
        tool_response = run_query_tool.invoke(modified_tool_call)
    elif response["type"] == "response":
        user_feedback = response["args"]
        tool_response = ToolMessage(
            content=user_feedback, 
            tool_call_id=tool_call["id"], 
            name=tool_call["name"]
        )
    else:
        raise ValueError(f"Unsupported interrupt response type: {response['type']}")

    state["messages"].append(tool_response)
    return state

Before executing the query, we use the interrupt function to explicitly pause the workflow. This gives an operator the chance to review, edit, or reject the queries, averting potentially destructive behavior.

Note

For more alternatives and details, refer to the human-in-the-loop guide.

Putting It All Together

from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()

@entrypoint(checkpointer=checkpointer)
def agent(state: AgentState) -> AgentState:
    # 1. Initialization
    state = list_tables(state).result()
    state = call_get_schema(state).result()
    
    # 2. Main Generation Loop
    while True:
        state = generate_query(state).result()
        last_message = state["messages"][-1]
        
        # If there are no tool calls, the LLM has delivered a final response
        if not getattr(last_message, "tool_calls", None):
            break
            
        # 3. Validation and Execution
        state = check_query(state).result()
        state = run_query(state).result()
        
    return state

We combine all tasks into a single comprehensive workflow using an @entrypoint wrapped function. The InMemorySaver checkpointer is required since the interrupt function pauses the execution flow, requiring state persistence between runs.

Running the Agent

import json

config = {"configurable": {"thread_id": "1"}}
question = "Which genre on average has the longest tracks?"

input_state = AgentState(messages=[HumanMessage(content=question)])

# Execution will stop and surface the interruption
result = agent.invoke(input_state, config)

print("INTERRUPTED:")
for action in result["__interrupt__"]:
    print(json.dumps(action.value, indent=2))

Invoking the agent kicks off the sequence. As designed, it stops upon reaching the run_query task and surfaces the tool call to await explicit review.

from langgraph.types import Command

# Resume logic with execution permission
result = agent.invoke(
    Command(resume={"type": "accept"}),
    config
)

# Output final messages
for msg in result["messages"]:
    msg.pretty_print()

We use Command to provide the human response (in this case, "accept") back into the graph, allowing it to resume operations and execute the validated query.

Key Takeaways

  • Functional API over Graph API: We used the LangGraph Functional API alongside @entrypoint and @task to define agents through sequential and logical flows, avoiding explicit state graph edges and retaining full control directly in Python loops.
  • Custom State Schema: Creating a simple TypedDict containing our AgentState list of messages simplifies the interactions across tasks rather than depending on predefined schemas.
  • Granular Agent Steps: Structuring an SQL interaction as distinct specific steps (getting schemas, rewriting queries, and running queries) enhances model reliability and lowers hallucinatory behavior.
  • Human-In-The-Loop: By yielding an interrupt() on the active run, we enforce a critical barrier between generating database queries and safely executing them. A checkpointer stops operations awaiting human validation via resume Command payloads.
