Retrieval Augmented Generation (RAG)

One of the most powerful applications enabled by LLMs is sophisticated question-answering (Q&A) chatbots.

Retrieval Augmented Generation, or RAG is a technique that enables an Agent to answer questions about specific source information.

  1. A RAG agent that executes searches with a simple tool. This is a good general-purpose implementation.
  2. A two-step RAG chain that uses just a single LLM call per query. This is a fast and effective method for simple queries.

Concepts

We will cover the following concepts:

  • Indexing: a pipeline for ingesting data from a source and indexing it. This usually happens in a separate process.

  • Retrieval and generation: the actual RAG process, which takes the user query at run time and retrieves the relevant data from the index, then passes that to the model.

Once we’ve indexed our data, we will use an agent as our orchestration framework to implement the retrieval and generation steps.

1. Documents and document loaders

  • What: A Document is a unit of text (page_content) plus optional metadata and id.
  • Why: LangChain’s retrieval and chains expect this format; metadata (e.g. source, page) lets you trace and filter chunks.
  • How (other sources): Document loaders — CSV, web, Notion, etc.
from langchain_core.documents import Document

# Example: create Documents by hand (page_content + optional metadata)
documents = [
    Document(
        page_content="Dogs are great companions, known for their loyalty and friendliness.",
        metadata={"source": "mammal-pets-doc"},
    ),
    Document(
        page_content="Cats are independent pets that often enjoy their own space.",
        metadata={"source": "mammal-pets-doc"},
    ),
]

Loading a PDF

  • What: PyPDFLoader produces one Document per PDF page.
  • Why: Page-level chunks are too big for precise retrieval; we split them next. Loading by page keeps metadata.page usable.

Splitting

  • What: RecursiveCharacterTextSplitter splits on separators (newlines, then spaces) until chunks ≤ chunk_size; chunk_overlap overlaps adjacent chunks.
  • Why: Full pages mix many ideas; smaller chunks let retrieval return only the relevant passage. Overlap avoids cutting sentences and keeps local context.
  • Why add_start_index: Puts the character offset in metadata so you can map chunks back to the original document. How to tune splitters.
  • Other splitters: CharacterTextSplitter, MarkdownHeaderTextSplitter.
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,   # overlap reduces risk of cutting mid-sentence
    add_start_index=True # store start_index in metadata for each chunk
)
all_splits = text_splitter.split_documents(docs)
print(len(all_splits))  # many more chunks than pages

2. Embeddings

  • What: Map text to fixed-size vectors (here 768-dim); same model for chunks and queries.

3. Vector stores

  • What: Stores (embedding, document) pairs and answers nearest-neighbor queries. We use InMemoryVectorStore (no DB).
  • Why: Enables fast similarity search over many chunks; production usually uses a persistent store (see below).
  • How (persistent / scale): Chroma, FAISS, Pinecone. Vector stores overview.
from langchain_core.vectorstores import InMemoryVectorStore

# InMemoryVectorStore uses the provided embeddings to embed documents on add
vector_store = InMemoryVectorStore(embeddings)
  • add_documents embeds each chunk with the store’s embedding model and indexes them. Returns document IDs.
ids = vector_store.add_documents(documents=all_splits)  # returns IDs for each doc

Query by string. The store embeds the query and returns top-k documents. similarity_search

# similarity_search(query, k=4) — returns top-k Documents;
results = vector_store.similarity_search("What is the main architecture proposed in the paper?")
print(results[0])

4. Retrievers

  • What: VectorStore.as_retriever() returns a Retriever that chains (e.g. RAG) call with a query and get documents.

  • Why: Chains need a single “retrieve” interface; search_type and search_kwargs control which vector-store method is used and with what args.

  • Options: search_type: "similarity" (default), "mmr", "similarity_score_threshold". Retrievers · How to use in RAG.

  • search_kwargs: e.g. k (top-k), fetch_k for MMR. Example: batch multiple queries.

# search_kwargs: e.g. k (top-k), fetch_k for MMR
retriever = vector_store.as_retriever(search_type="similarity", search_kwargs={"k": 1})
out = retriever.batch([
    "What is the main architecture proposed in the paper?",
    "What is self-attention?",
])
print(out[0][0].page_content[:200], "\n---\n", out[1][0].page_content[:200])

5. Retrieval and generation

RAG applications commonly work as follows:

  1. Retrieve: Given a user input, relevant splits are retrieved from storage using a Retriever.
  2. Generate: A model produces an answer using a prompt that includes both the question with the retrieved data.

Now we’ll add the application logic: take a user question, search for relevant documents (using the vector store we built above), pass the retrieved documents and question to a model, and return an answer.

We demonstrate a RAG agent that uses a retrieval tool—a general-purpose implementation that can perform multiple retrieval steps per query.

Chat model for RAG

We need a chat model to generate answers from the retrieved context. Install and configure once (e.g. OpenRouter or OpenAI). Get your key at OpenRouter or use OpenAI.

RAG agent

One formulation of a RAG application is a simple agent with a tool that retrieves information. We implement a tool that wraps our vector store:

from langchain.tools import tool

@tool(response_format="content_and_artifact")
def retrieve_context(query: str):
    """Retrieve information to help answer a query."""
    retrieved_docs = vector_store.similarity_search(query, k=2)
    serialized = "\n\n".join(
        (f"Source: {doc.metadata}\nContent: {doc.page_content}")
        for doc in retrieved_docs
    )
    return serialized, retrieved_docs
Tip

The tool decorator can attach raw documents as artifacts to each ToolMessage, so you can use document metadata in your app. You can also add more arguments (e.g. section: Literal["beginning", "middle", "end"]) to let the LLM refine search parameters.

Given this tool, we construct the agent:

from langchain.agents import create_agent

tools = [retrieve_context]
prompt = (
    "You have access to a tool that retrieves context from the indexed documents. "
    "Use the tool to help answer user queries."
)
agent = create_agent(model, tools, system_prompt=prompt)

Test the agent with a question that can benefit from retrieval (e.g. over the PDF we indexed):

query = (
    "What is the main architecture proposed in the paper?\n\n"
    "Once you have that, look up how attention is defined."
)

for event in agent.stream(
    {"messages": [{"role": "user", "content": query}]},
    stream_mode="values",
):
    event["messages"][-1].pretty_print()

The agent (1) generates a query to search the documents, (2) can perform follow-up retrievals if needed, and (3) answers using the retrieved context. For more control (e.g. grading relevance, rewriting queries), see LangGraph Agentic RAG.
